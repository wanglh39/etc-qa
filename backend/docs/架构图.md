# ETC客服QA智能检索系统 — 整体架构图

## 核心流程总览

```
客服输入原始问题
        │
        ▼
Agent标准化（清洗+规整）→ 输出标准化问题
        │
        ▼
RAG检索（用标准化问题去检索，效果更好）
        │
        ├── 命中 → 返回答案
        └── 未命中 → 提交工单系统 → 工单处理 → 拉取已处理工单
                                                        │
                                                        ▼
                                                Agent入库预处理（规整+分类）
                                                        │
                                                        ▼
                                                周批量去重 → 入库
```

## 两条核心链路

### 链路1：检索流程（/api/v1/query）

```
客服输入原始问题
    │
    ▼
Agent标准化（preprocess_agent，2步）
├── clean_text：防御性清洗（空格/标点/数字格式+工单前缀）
└── standardize_query：规则清洗+LLM评判工具，保留品牌名/疑问词
    │
    ▼
输出标准化问题
    │
    ▼
RAG检索
├── Embedding编码（bge-large-zh-v1.5, 1024维, 加QUERY_PREFIX）
├── 获取active_qa_ids（MySQL WHERE status='active'）
├── 双路并行召回
│   ├── 向量检索：Milvus余弦相似度，Top-10（is_hyde=false过滤，active_qa_ids过滤）
│   └── BM25检索：jieba分词 + BM25Okapi，Top-10（仅active记录建索引）
├── RRF合并（k=60），去重合并为统一候选池
├── Reranker精排（bge-reranker-large），按分数重排
└── 阈值判定（模块4：差值模式，置信度作为审核优先级，都返回候选给客服看）
    ├── 差值 = Top1分数 - Top2分数（区分度高=Top1显著优于其他）
    ├── 双条件：差值 >= gap_X AND Top1 >= floor_X（防止"两个都很差但差值大"误判）
    ├── 高置信：差值>=0.15且Top1>=0.5 → 返回Top-3，客服简单看看
    ├── 中置信：差值>=0.08且Top1>=0.3 → 返回Top-5，标记需认真看
    ├── 低置信：差值>=0.03且Top1>=0.15 → 返回Top-10，标记需认真看
    └── 无匹配：不满足以上 → 返回Top-10，标记none
    单候选：差值默认1.0（但仍需Top1>=floor_high才算高置信）
    mode=absolute时回退为纯绝对分数模式（向后兼容）
    工单由客服手动提交，不再自动触发
    │
    ▼
MySQL查完整记录 → 返回结果给客服
```

### 链路2：入库预处理流程（/api/v1/agent/process）

```
已处理工单数据（问题+答案，格式因人而异）
    │
    ▼
clean_text（防御性清洗）
├── 合并多余空格
├── 重复标点归一
└── 数字分隔符修正 + 工单前缀清洗
    │
    ▼
structure_ingest（入库前标准化+分类，PromptEngine模板+StructuredOutput结构化输出）
├── 提示词渲染：PromptEngine从DB加载模板→jinja2渲染（enterprise_name等变量自动替换）
├── 结构化输出：LLM返回Pydantic Schema（StructureIngestOutput），字段自动校验
├── 问题改写：工单描述 → 知识库标准问题格式（5-30字，提问式）
├── 答案结构化：自由文本 → answer + internal_process + feedback_dept
├── 分类匹配：从知识库分类体系动态选择category_l1/category_l2（从MySQL加载）
├── 分类置信度：输出category_confidence（0.0~1.0），低于阈值触发needs_review人工审核
├── 参考示例：从config_center读取模板化示例（不写死prompt，自动跟随业务变化）
├── 关键词列表：从config.yaml读取forbidden_new_kws/must_preserve_kws
├── 支持work_order_context字段（工单额外上下文传入prompt）
└── 输出JSON直接对齐MySQL+Milvus字段（Pydantic校验保证字段完整性）
    │
    ▼
hyde_rewrite（条件改写：两层判断跳过不需要改写的问题）
├── 第1层规则预判（0 token）：问题5-15字+含品牌词+含疑问词 → 直接跳过
├── 第2层LLM判断：规则无法判定时，调LLM输出HydeJudgeOutput(need_rewrite+reason)
├── 需要改写时：站在用户角度生成3种口语化问法，保留品牌名/疑问词/具体业务细节
├── 答案截断为150字摘要
└── 不需要改写时：跳过，节省LLM调用成本
    │
    ▼
输出标准化待审核条目 → 周批量去重 → 入库
```

## 工单闭环流程

```
客服提问 → RAG未命中 → 提交工单系统（调外部API）
                               │
                               ▼
                     本地work_orders表存记录（status=submitted）
                               │
                               ▼
                     工单系统处理（外部系统，我们不管）
                               │
                               ▼
                     定时拉取已处理工单（调外部API）
                               │
                               ▼
                     更新本地记录（status=answered）
                               │
                               ▼
                     Agent预处理：clean_text → structure_ingest
                               │
                               ▼
                     更新本地记录（status=processed）
                               │
                               ▼
                     周批量去重（两轮）
                     ├── 第一轮：新问题 vs 已有知识库（RAG检索）
                     └── 第二轮：新问题之间互相比对（numpy余弦相似度）
                         ├── 问题相似+答案相似 → 真重复
                         └── 问题相似+答案不同 → 不去重（不同问答对）
                               │
                               ▼
                     去重后入库（status=imported/rejected）
                               │
                               ▼
                     双库入库（batch_import.py）
                     ├── MySQL：insert_qa()
                     ├── Milvus：insert()（原始+HyDE向量）
                     └── 一致性校验（MySQL qa_id ↔ Milvus qa_id）
                               │
                               ▼
                     定期清理：删除imported/rejected记录
```

## HyDE两步分离流程

```
第1步：hyde_generate.py（LLM+Embedding，不依赖Milvus）
├── 读取MySQL qa_pairs
├── 调用hyde_rewrite生成假设性问题
├── Embedding编码
└── 缓存到JSON文件（scripts/eval_output/hyde_cache.json）

第2步：hyde_insert.py（读缓存→Milvus，不依赖LLM）
├── 读取缓存JSON
├── 批量插入Milvus（is_hyde=true）
└── 每批后关连接+延时3秒（避免gRPC too_many_pings）
```

## Agent两个图的对比

| | preprocess_agent（检索前标准化） | ingest_agent（入库前预处理） |
|---|---|---|
| 触发时机 | 每次客服提问时 | 工单办结后/新问题入库前 |
| API | /api/v1/query（内部调用） | /api/v1/agent/process |
| 步骤 | clean_text → standardize_query | clean_text → structure_ingest → hyde_rewrite |
| 步骤数 | 2步 | 3步 |
| 目的 | 把问题标准化，提高RAG检索命中率 | 把工单数据规整/分类/HyDE改写，准备入库 |
| 是否调LLM | 规则优先，LLM评判兜底 | 是（规整+分类+HyDE） |
| 提示词 | PromptEngine渲染+StructuredOutput优先 | PromptEngine渲染+StructuredOutput优先 |
| HyDE改写 | 不涉及 | 条件改写：规则预判→LLM判断，跳过不需要改写的问题 |
| 分类置信度 | 不涉及 | 输出category_confidence，低置信度触发人工审核 |

## 评估体系

```
评估脚本
├── eval_rag.py          4配置消融对比+R@1/R@3/R@5/R@10/MRR+失败case分析
├── eval_structure_ingest.py  入库改写质量评估（语义保持+格式规范+分类+答案结构化）
└── eval_langsmith.py    LangSmith evaluate API（3个评估器：R@1/R@3/MRR，无LangSmith时自动降级本地跑）

关键发现：
- 加权RRF权重对结果无影响（Reranker排序覆盖了融合差异），保持标准RRF
- R@1失败主因：相似报错互相抢top1（17/28条），Reranker分数差距极小
- HyDE prompt改进：用户视角+答案摘要+保留品牌名/疑问词/具体细节
- structure_ingest合并classify：一次LLM调用输出完整JSON，ingest_agent从4步变3步
```

配置读取优先级：**DB > YAML > 代码默认值**
- DB有值 → 用DB（支持运行时热更新）
- DB无值 → 用YAML（零迁移成本，YAML是兜底）
- YAML也无 → 用代码默认值

热更新机制：
- `PUT /api/v1/config/{key}` → 写MySQL + 自动失效缓存
- `POST /api/v1/config/reload` → 强制全量刷新
- TTL 60s兜底，即使忘了调reload也会自动刷新

## 模块2/5改造说明（提示词模板化+结构化输出+HyDE条件改写）

### 模块2：提示词模板化 + 结构化输出

**改造前的问题：**
- 提示词（prompt）写死在代码里，改一个字都要改代码重新部署
- LLM返回的是纯文本JSON，要手动解析，容易出错（字段缺失、格式不对）
- 示例（few-shot examples）也写死在代码里

**改造后做了什么：**

1. **新建`agent/prompt_engine.py`（提示词模板引擎）**
   - 用jinja2模板引擎渲染提示词，支持`{{enterprise_name}}`、`{{brand_keywords_str}}`等变量自动替换
   - 模板优先从DB加载（`prompt_templates`表），DB没有就用代码里的fallback
   - 60秒TTL缓存，线程安全，改了DB模板后最多60秒自动生效
   - 这样运维人员在管理后台改提示词，不需要改代码重新部署

2. **新建`agent/output_schemas.py`（4个结构化输出Schema）**
   - `StandardizeOutput`：标准化判断结果（need_rewrite + reason + rewritten）
   - `StructureIngestOutput`：入库结构化结果（question + answer + category_l1/l2 + **category_confidence** + internal_process + feedback_dept）
   - `HydeJudgeOutput`：HyDE是否需要改写的判断（need_rewrite + reason）
   - `HydeRewriteOutput`：HyDE改写结果（questions列表）
   - 用Pydantic定义字段约束：`min_length=1`（问题/答案不能为空）、`ge=0.0/le=1.0`（置信度范围）

3. **改造`agent/llm.py`新增`get_structured_llm()`**
   - 调用LangChain的`with_structured_output(schema)`，让LLM直接返回Pydantic对象（不用手动解析JSON）
   - DeepSeek支持tool_call模式，结构化输出更稳定
   - 不支持时自动降级为普通LLM+JSON解析（兼容性兜底）

4. **改造三个processor（standardize_query / structure_ingest / hyde_rewrite）**
   - 提示词改用PromptEngine渲染（不再写死）
   - 优先用StructuredOutput获取结构化结果（Pydantic自动校验字段）
   - 不支持时降级为JSON解析（兼容性兜底）
   - few-shot示例也模板化（从config_center读取，可热更新）

### 模块5：HyDE条件改写

**改造前的问题：**
- 每条QA都调LLM生成HyDE假设性问题，即使问题已经很标准（如"ETC怎么注销"）
- 浪费LLM调用成本，50条数据可能有一半不需要改写

**改造后做了什么：**

1. **`hyde_rewrite.py`新增`_judge_need_rewrite()`两层判断**
   - **第1层规则预判（0 token，不调LLM）：**
     - 问题长度5-15字 + 包含品牌词(ETC) + 包含疑问词(怎么/如何/为什么) → 判定"不需要改写"，直接跳过
     - 这一层完全免费，能跳过80%的标准问题
   - **第2层LLM判断（规则无法判定时才调LLM）：**
     - 调LLM输出`HydeJudgeOutput(need_rewrite, reason)`
     - 用于规则覆盖不到的边界情况（如问题20字但很口语化）

2. **`hyde_generate.py`批量模式遵守上限**
   - 新增`max_rewrite_per_batch`配置（默认50），批量生成时不超过这个数
   - 统计generated/skipped数量，方便监控跳过率

3. **config.yaml新增条件改写参数**
   - `conditional: true`（开启条件改写）
   - `max_questions_per_qa: 3`（每条QA最多生成3个假设性问题）
   - `max_rewrite_per_batch: 50`（每批最多改写50条）
