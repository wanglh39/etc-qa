# 数据规范与入库流水线

## 一、数据准入规范

新数据入库前必须满足以下条件，否则拒绝入库：

### 1.1 必填字段

| 字段 | 类型 | 要求 | 示例 |
|------|------|------|------|
| question | string | 5-50字，提问式，有业务关键词 | "ETC重复扣费怎么退款" |
| answer | string | 10-500字，面向客户的完整话术 | "核实扣费记录，确认重复扣费后3个工作日退款至原账户" |

### 1.2 选填字段

| 字段 | 类型 | 要求 | 示例 |
|------|------|------|------|
| category_l1 | string | 必须在分类体系内 | "售后业务" |
| category_l2 | string | 必须在分类体系内且属于category_l1 | "账单类" |
| internal_process | string | 给客服看的操作步骤 | "核实扣费记录→确认重复→发起退款" |
| feedback_dept | string | 涉及部门/群/模板 | "财务组" |

### 1.3 质量门禁

| 检查项 | 规则 | 不通过处理 |
|--------|------|-----------|
| 问题长度 | 5-50字 | 拒绝入库 |
| 答案长度 | 10-500字 | 拒绝入库 |
| 问题去重 | 与已有知识库相似度<0.92 | 标记重复，不入库 |
| 幻觉检测 | 改写不得引入原文未提及的业务概念 | 回退为原始问题，标记需人工审核 |
| 关键词保留 | must_preserve_kws中的词在原文出现时改写必须保留 | 标记需人工审核 |
| 分类合法性 | category_l1/l2必须在分类体系内 | 使用默认分类，标记需人工审核 |

## 二、数据格式规范

### 2.1 CSV入库格式

新数据以CSV文件提供，格式如下：

```csv
question,answer,category_l1,category_l2,internal_process,feedback_dept
"ETC重复扣费怎么退款","核实扣费记录，确认重复扣费后3个工作日退款至原账户","售后业务","账单类","核实扣费记录→确认重复→发起退款","财务组"
```

要求：
- CSV编码：UTF-8
- question和answer字段**不能为空**
- 含逗号的字段用双引号包裹
- 不允许HTML标签、连续空格、不可见字符

### 2.2 API入库格式

通过 `POST /api/v1/add` 入库，JSON格式：

```json
{
  "question": "ETC重复扣费怎么退款",
  "answer": "核实扣费记录，确认重复扣费后3个工作日退款至原账户",
  "category_l1": "售后业务",
  "category_l2": "账单类",
  "internal_process": "核实扣费记录→确认重复→发起退款",
  "feedback_dept": "财务组"
}
```

### 2.3 工单入库格式

通过 `POST /api/v1/agent/process` 入库，系统自动执行3步预处理：

```json
{
  "question": "客户张三反馈ETC重复扣费了上个月在同一高速口扣了两次",
  "answer": "核实扣费记录，确认重复扣费后退款",
  "context": "工单类型=通行异常/多扣费，流转至=财务组"
}
```

## 三、入库流水线

### 3.1 完整流水线（6步）

```
原始数据
  │
  ▼
[Step 1] 数据清洗 (clean_text)
  │  - 去除客户隐私信息（电话/姓名/车牌号）
  │  - 去除HTML标签/不可见字符
  │  - 业务清洗规则（从config_center读取）
  │
  ▼
[Step 2] 结构化规整 (structure_ingest)
  │  - LLM改写为标准问题格式
  │  - LLM分类（category_l1/l2）
  │  - 分离answer/internal_process/feedback_dept
  │  - 幻觉检测+关键词保留校验
  │
  ▼
[Step 3] 去重检查 (dedup)
  │  - 第一轮：新问题 vs 已有知识库（余弦相似度>0.92 → 重复）
  │  - 第二轮：新问题之间互相比对
  │
  ▼
[Step 4] 双库写入 (insert)
  │  - MySQL qa_pairs表写入
  │  - Milvus qa_vectors向量插入
  │  - BM25索引重建
  │
  ▼
[Step 5] HyDE增强 (hyde)
  │  - LLM生成假设性问题（3种改写）
  │  - 编码为向量插入Milvus（is_hyde=true）
  │
  ▼
[Step 6] 质量校验 (verify)
     - MySQL与Milvus数据一致性检查
     - 向量可检索性验证
     - 输出入库报告
```

### 3.2 快速入库（跳过LLM步骤）

当数据已经是标准格式（人工审核过的CSV），可跳过Step 2和Step 5：

```bash
python scripts/pipeline/ingest_pipeline.py --csv data/processed/qa_filled.csv --skip-llm
```

### 3.3 完整入库（含LLM处理）

当数据是原始工单格式，需要LLM规整+HyDE：

```bash
python scripts/pipeline/ingest_pipeline.py --csv data/eval/work_orders_200.csv --full
```

## 四、数据运营规范

### 4.1 新增知识流程

1. **收集**：客服反馈/工单处理结果/业务部门提供
2. **整理**：按2.1或2.2格式整理
3. **入库**：走流水线（自动清洗+规整+去重+写入+HyDE）
4. **验证**：检查入库报告，确认无错误
5. **评估**：定期跑eval_rag.py验证检索效果

### 4.2 知识更新流程

1. **标记过时**：`PUT /api/v1/qa/status` → deprecated
2. **新增替代**：走新增流程入库新版本
3. **验证**：确认新知识可检索，旧知识已过滤

### 4.3 知识删除流程

1. **软删除**：`PUT /api/v1/qa/status` → deprecated/archived
2. **验证**：确认检索结果不再包含该知识
3. **注意**：Milvus向量不物理删除，通过active_qa_ids过滤

### 4.4 定期维护

| 频率 | 操作 | 命令 |
|------|------|------|
| 每周 | 工单去重 | `python scripts/maintenance/weekly_dedup.py` |
| 每月 | RAG评估 | `python scripts/eval/eval_rag.py 200` |
| 每月 | HyDE全量更新 | `python scripts/pipeline/hyde_generate.py && python scripts/pipeline/hyde_insert.py` |
| 每季度 | 知识库审计 | 检查deprecated/archived比例，清理长期无用知识 |
