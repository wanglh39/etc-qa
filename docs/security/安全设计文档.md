# 安全设计文档

## 一、认证体系

### 1.1 JWT 认证

**认证流程**：

```
用户登录 → POST /api/auth/login → 校验密码 → 生成 JWT → 返回 token
    ↓
后续请求 → Authorization: Bearer <token> → JWT 解码 → 查 DB users 表 → 注入 user 对象
    ↓
DB 异常 → 退回硬编码 USERS 兜底（保证 DB 宕机不锁死）
```

**Token 规格**：
- 算法：HS256
- 有效期：24 小时
- 载荷：`{ username, role, dept, exp, impersonated_by? }`
- 存储：前端 sessionStorage（非 localStorage，关浏览器自动清除）

**兜底机制**：
- 登录时优先查 MySQL `users` 表（status=active + verify_password）
- DB 不可用或用户不存在时退回 `jwt_utils.USERS` 硬编码兜底
- 保证 DB 宕机时系统不锁死

### 1.2 模拟登录

**接口**：`POST /api/auth/impersonate`（仅 superadmin）

**流程**：
1. 超管调用接口，指定 `target_username`
2. 后端生成目标角色 token，载荷加 `impersonated_by: "superadmin"` 字段
3. 写入操作日志审计（operator/action/target）
4. 前端用目标角色 token 进入系统，顶部显示橙色提示栏
5. 一键退出模拟，恢复超管 token

**安全约束**：
- 仅 superadmin 可调用
- 模拟 token 含 `impersonated_by` 字段，可追溯
- 操作日志记录模拟行为

## 二、RBAC 权限体系

### 2.1 角色定义

5 角色 RBAC，按企业级四层分离设计：

| 角色 | 定位 | 权限范围 | 默认首页 |
|------|------|---------|---------|
| superadmin | 系统管理层 | 账号/角色/日志/模拟登录 + 所有页面 | /workbench/admin/account |
| admin | 业务管理层 | 数据看板/审核/知识库/分类/配置 | /workbench/admin/dashboard |
| ops | 运维层 | 数据看板/系统状态/监控/调度/告警 | /workbench/admin/status |
| service | 操作层（客服） | 客服工作台 | /service |
| dept | 操作层（部门） | 部门工单处理 | /dept/handle/{dept} |

**设计原则**：
- 业务管理员(admin)不管运维，运维工程师(ops)不管业务
- 超级管理员(superadmin)只管"谁能干什么"，不直接管业务也不直接管运维
- superadmin 可访问所有页面（管理/审计需要），可通过模拟登录以其他角色身份查看系统

### 2.2 权限矩阵

**后端 API 权限**（`require_role()` 装饰器）：

| 模块 | 端点 | 权限 |
|------|------|------|
| 认证 | /api/auth/login | 公开 |
| 认证 | /api/auth/verify | 已登录 |
| 认证 | /api/auth/impersonate | superadmin |
| QA 检索 | /api/query | 已登录 |
| 新增知识 | /api/add | admin, superadmin |
| QA 状态 | /api/qa/status | admin, superadmin |
| QA 删除 | /api/qa/{id} DELETE | admin, superadmin |
| 配置管理 | /api/config/* | admin, superadmin |
| 分类管理 | /api/categories POST/PUT/DELETE | admin, superadmin |
| 统计 | /api/stats | admin, superadmin, ops |
| 审核历史 | /api/audit/history | admin, superadmin |
| 用户管理 | /api/users | superadmin |
| 角色管理 | /api/roles | superadmin |
| 操作日志 | /api/operations | superadmin |
| 调度管理 | /api/scheduler/* | admin, superadmin, ops |
| 告警管理 | /api/alerts/* | admin, superadmin, ops |
| 系统运维 | /api/system/* | superadmin, ops |

**前端路由权限**（`meta.roleAuth`）：

```
meta: { roleAuth: 'admin,ops' }    → admin + ops + superadmin
meta: { roleAuth: 'superadmin' }   → 仅 superadmin
meta: { roleAuth: 'ops' }          → ops + superadmin
meta: { roleAuth: 'all' }          → 所有已登录角色
superadmin → 路由守卫直接放行所有页面
```

### 2.3 前后端权限一致性

**双重校验**：前端 roleAuth + 后端 require_role

| 检查项 | 后端 | 前端 | 一致性要求 |
|--------|------|------|-----------|
| API 端点权限 | `require_role("admin")` | 调用该 API 的页面 roleAuth | 前端能访问的角色后端也必须放行 |
| 新增页面 | 无 | 路由 meta.roleAuth + 菜单 | 菜单只给有权限的角色显示 |
| 新增角色 | init_db.py 种子 + jwt_utils.py | login.vue 跳转 + getDefaultPath | 5 处都要改 |

**典型 bug**：前端 roleAuth 放了 ops 但后端 require_role 没加 ops → 前端能进页面但 API 返回 403

### 2.4 路由守卫流程

```
1. 去登录页 → 放行
2. 无 token → 跳登录页
3. JWT 过期检查 → 解码 exp，过期则清理跳登录
4. 首次导航 → 调后端 /api/auth/verify 验证 token
5. 角色信息缺失 → 清理跳登录
6. 权限校验：
   - superadmin → 放行所有
   - roleAuth 未设置或 'all' → 放行
   - 其他 → 检查 roleAuth 逗号分隔列表
   - 不通过 → 跳回该角色默认首页
```

## 三、数据安全

### 3.1 密码安全

- 存储：bcrypt 哈希（不存明文）
- 传输：HTTPS（生产环境）
- 重置：仅 superadmin 可重置他人密码

### 3.2 敏感信息

- API Key / 数据库密码：存 `.env`，不提交 Git
- `.env.example`：维护模板，列出变量名但不含值
- config.yaml：敏感值用 `${ENV_VAR:default}` 语法

### 3.3 前端安全

- Token 存 sessionStorage（非 localStorage），关浏览器自动清除
- 路由守卫首次导航调 `/api/auth/verify` 验证 token 有效性
- 401 → 清 store + 跳登录
- 403 → 权限不足提示
- 配置读取敏感字段脱敏

### 3.4 限流防刷

| 端点 | 限制 |
|------|------|
| /api/auth/login | 30次/60s/IP、5次/60s/用户 |
| /api/query | 30次/60s |
| /api/agent/process | 20次/60s |
| /api/asr | 10次/60s |
| /api/asr/query | 10次/60s |

## 四、操作审计

### 4.1 操作日志

`operation_log` 表记录所有管理操作：

| 字段 | 说明 |
|------|------|
| operator | 操作人 |
| action | 操作类型（create_user/update_role/impersonate 等） |
| target_type | 目标对象类型 |
| target_id | 目标对象 ID |
| detail | 操作详情 |
| ip | 操作 IP |
| created_at | 操作时间 |

### 4.2 审核日志

`audit_log` 表记录 QA 审核操作：

| 字段 | 说明 |
|------|------|
| qa_id | 关联 QA |
| result | 审核结果（入库/驳回） |
| operator | 审核人 |

### 4.3 模拟登录审计

模拟登录行为写入操作日志，含 `impersonated_by` 字段，可追溯超管模拟操作。
