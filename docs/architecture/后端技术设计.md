# 客服工单流转系统优化 — 挑战杯技术文稿

## 一、项目概述

### 1.1 项目背景

传统企业客服工单处理模式存在重复咨询量大、工单流转链路长、部门处理冗余、人工成本高、问题响应时效慢等核心痛点。海量标准化、重复性的用户咨询问题，仍需通过CRM系统发起工单、跨部门流转处理，占用客服及业务部门大量人力，导致简单问题处理效率极低；同时新增、个性化问题缺乏标准化沉淀机制，历史优质解决方案无法复用，长期造成客服服务质量参差不齐、用户等待时长过长、企业运维成本居高不下。

为解决以上行业痛点，本系统基于阿里云NLS语音识别API+RAG+Agent数据周期处理，对传统CRM工单体系进行智能化升级，实现语音问题智能提炼、分层自动化处理，缩短服务响应周期、沉淀企业专属客服知识库。

### 1.2 产品定位

本产品是嵌入企业现有CRM工单系统的智能客服问题处理辅助系统，不替代原有CRM工单流转体系，而是做前置语音识别、问题智能提炼、智能分流与知识沉淀优化。

- **针对高频重复问题**：通过语音识别API总结标准化问题，无需创建工单、无需人工介入，通过RAG知识库直接输出历史最优解决方案，经人工审核，秒级响应用户。
- **针对新增/非重复复杂问题**：语音提炼后的标准化问题，通过Agent完成数据去重、文本清洗、语义规整，经人工审核后周期性入库迭代，持续扩充知识库，逐步降低重复工单量。

最终实现「问题智能提炼、重复问题智能化秒回、复杂问题标准化流转、服务知识常态化沉淀」的闭环体系。

### 2.2 数据存储策略

采用**MySQL+Milvus双库协同**架构：

- **MySQL**：存储完整QA记录（问题、答案、分类、内部流程、反馈部门、状态等），同时存储业务配置（关键词、正则规则）、提示词模板、用户账号（users表）、角色（roles表）、告警事件（alert_events表）
- **Milvus**：仅存储问题向量（1024维），用于语义检索
- **关联方式**：通过qa_id字段关联，MySQL为主、Milvus为辅
- **鉴权策略**：登录时优先查users表（status=active+verify_password），DB不可用或用户不存在时退回硬编码USERS兜底，保证DB宕机不锁死
- **角色分离**：5角色RBAC体系（superadmin/ops/admin/service/dept），superadmin管系统+模拟登录，ops管运维，admin管业务+内容，/users /roles 接口仅superadmin可调用
- **模拟登录**：POST /api/auth/impersonate，仅superadmin可调，生成目标角色token（含impersonated_by字段），写入操作日志审计

这种设计的优势：
1. 答案文本较长（200-600字），存向量库浪费空间且无法全文检索
2. 问题较短（5-15字），向量化后语义匹配效果好
3. 检索时"问题匹配问题"，语义对齐更准确
4. 答案变更不影响向量索引，只需更新MySQL

### 2.3 配置分层架构

系统采用三层配置体系，优先级为 **DB > YAML > 代码默认值**：

| 配置层 | 存储位置 | 内容 | 更新方式 |
|--------|---------|------|---------|
| 业务规则 | MySQL system_config表 | 关键词列表、正则规则、分类体系 | API热更新，无需重启 |
| 基础设施 | config/*.yaml | 数据库地址、API配置、阈值参数 | 修改后需重启 |
| 敏感信息 | .env | API Key、数据库密码 | 不提交Git |

配置中心（config_center.py）实现统一读取层，内置60秒TTL缓存+线程安全。业务人员通过管理API修改关键词/规则后，自动刷新缓存，无需重启服务。不同企业部署时只需修改业务规则层即可适配，代码零改动。

### 2.4 应用生命周期管理

系统采用**FastAPI lifespan + FileLock进程锁**的模型生命周期管理方案，解决开发环境uvicorn热重载（reload=true）启动主+子双进程时的GPU显存浪费和Milvus锁冲突问题：

```
uvicorn reload=true
┌─────────────────────────────────────────┐
│ 主进程 (Reloader)                       │
│ - 只监控文件变化                        │
│ - 不加载模型 (lifespan不触发)           │
│ - 不初始化Milvus                        │
└──────────┬──────────────────────────────┘
           │ fork
┌──────────▼──────────────────────────────┐
│ 子进程 (Server)                         │
│ - lifespan startup:                     │
│   ├─ 加载Embedding/Reranker模型(GPU)    │
│   ├─ 初始化MySQL/Milvus连接             │
│   ├─ FileLock进程锁保护Milvus初始化     │
│   ├─ RAG预热（触发load_collection）     │
│   ├─ ASR预热（如启用）                  │
│   └─ 启动定时调度器（APScheduler）      │
│ - 接受请求 → 推理                       │
│ - lifespan shutdown:                    │
│   ├─ 停止调度器                         │
│   └─ 关闭Milvus连接，释放资源           │
└─────────────────────────────────────────┘
```

- **lifespan管理**：create_service()在FastAPI lifespan中执行，只有server子进程触发，reloader主进程不加载模型
- **FileLock进程锁**：FileLock(tempdir/etc_qa_milvus_init.lock, timeout=30)串行化Milvus初始化，防止reload重启时新旧子进程争抢SQLite文件锁
- **workers=1**：GPU显存有限（8GB），只加载一份模型，多worker会各自占一份显存

这种设计的优势：
1. 主进程不加载模型，GPU显存只占一份，避免显存浪费
2. FileLock串行化Milvus初始化，避免SQLite文件锁冲突
3. 保留reload热重载功能，开发体验不受影响
4. lifespan shutdown自动清理Milvus连接，无资源泄漏

### 3.2 语音识别模块（ASR）

系统采用阿里云NLS（自然语言交互）API实现实时语音识别，支持客服语音输入，实现"语音→文字→检索"的端到端能力。

**技术方案**：

- 语音识别引擎：阿里云NLS实时语音识别API（WebSocket协议，wss://nls-gateway.cn-shanghai.aliyuncs.com）
- 热词表：在阿里云NLS控制台配置热词表（ETC/OBU/蓝牙/95022等22个领域专有名词），通过hotwords_id传入，提升专有名词识别准确率
- 领域纠错表：针对行业专有名词的识别纠错（如"一体机"→"ETC""欧比优"→"OBU""蓝呀"→"蓝牙"等），配置在config/asr.yaml，支持DB动态覆盖，不同企业部署时只需替换纠错表
- Token鉴权：通过aliyunsdkcore获取NLS Token，自动缓存+提前刷新（有效期前60秒续期）

**API设计**：

- POST /asr：上传音频→识别→纠错→返回文本
- GET /asr/health：ASR API连通性检查
- 识别结果自动送入/query链路，实现语音→检索的端到端体验

**测试验证**：20条真实客服问题音频测试，全部正确识别，CER（字符错误率）接近0。

**WebSocket流式识别**：

- 端点：/ws/asr/stream，全双工WebSocket连接，支持实时语音流输入和识别结果流式返回
- 阿里云NLS流式模式（AliCloudStreamingBackend）：后端WebSocket接收前端音频帧 → 转发阿里云NLS WebSocket → 中间结果on_partial/句子结束on_final回调 → 纠错表应用

- 协议消息：
  - 客户端→服务端：bytes（音频帧）+ JSON控制消息（config/flush/select_answer/reset/clear_cache/clear_context）

- 自动检索：识别final文本后自动触发RAG检索，返回query_result消息携带candidates候选答案列表

**前端流式ASR接入**：

- useStreamingASR composable（src/composables/useStreamingASR.ts）：封装WebSocket连接+麦克风采集+重采样16kHz+Int16 PCM转换+消息处理，对外暴露recording/partialText/fullText/queryResult等响应式状态

- Vite proxy配置：/ws路径代理到后端WebSocket端点，ws: true启用WebSocket代理

### 3.3 Agent标准化预处理

客服输入的原始问题往往包含口语化表达、填充词、客户隐私信息等噪声，直接用于检索会大幅降低匹配准确率。系统通过两步Agent预处理将问题标准化。

**第一步：clean_text（防御性清洗）**

- 合并多余空格
- 重复标点归一（"？？？"→"？"）
- 数字分隔符修正
- 客户隐私信息清洗（去除"客户张三（电话：138xxx）反馈："等前缀）
- 业务特定清洗规则（从config_center动态加载，不同企业可配置不同规则）

**第二步：standardize_query（智能规整）**

采用"规则优先+LLM兜底"的分层漏斗策略：

- **规则清洗（0 token，不调LLM）**：
  - 去除口语填充词（"我想问一下""麻烦问下""你好"等，正则匹配，规则可配置）
  - 同义替换（"怎么办理"→"如何办理""咋整"→"如何处理"等，配置化规则表）
  - 品牌词/疑问词保留检测

- **LLM评判（规则无法判定时才调LLM）**：
  - 当问题长度>30字或规则无法判断是否需要改写时，调用LLM
  - LLM输出结构化结果StandardizeOutput（need_rewrite + reason + rewritten + rewrite_confidence）
  - 改写置信度<0.5时拒绝改写，回退为规则清洗结果
  - 幻觉检测：改写不得引入原文未提及的业务概念（forbidden_new_kws列表校验）
  - 关键词保留校验：must_preserve_kws中的词在原文出现时改写必须保留

**设计亮点**：规则清洗覆盖80%的常见问题，节省LLM调用成本；LLM仅在边界情况下介入，兼顾效率和质量。分层漏斗架构确保简单问题零token处理，复杂问题有LLM兜底。

### 3.4 RAG智能检索引擎

标准化后的问题进入RAG检索引擎，采用"双路召回+RRF融合+Reranker精排"的三级检索架构：

**第一级：双路并行召回**

- **向量召回（Milvus）**：通过SiliconFlow API调用bge-large-zh-v1.5将标准化问题编码为1024维向量，在Milvus中做余弦相似度检索，返回Top-10候选。查询时加QUERY_PREFIX提升检索效果。自动过滤is_hyde=false（只查原始问题向量）和active_qa_ids（排除软删除记录）。

- **BM25召回（jieba + rank_bm25）**：对标准化问题做jieba分词，用BM25Okapi算法做关键词匹配，返回Top-10候选。BM25索引在服务启动时从MySQL构建，仅索引status=active的记录。BM25弥补向量检索在专有名词、缩写等场景下的不足。

**第二级：RRF融合**

两路召回结果通过Reciprocal Rank Fusion（RRF，k=60）合并为统一候选池，去重后保留所有来源的候选。RRF的优势是不依赖绝对分数，只依赖排名，对两路召回的分数尺度差异具有天然鲁棒性。

**第三级：Reranker精排**

通过SiliconFlow API调用bge-reranker-v2-m3对候选池做精排，将"问题-候选问题"对输入模型，输出相关性分数，按分数降序重排。Reranker能捕捉语义细微差异，显著提升Top1准确率。多key负载均衡：最长空闲优先选key，429/5xx自动冷却切下一个。

### 3.5 阈值判定系统

Reranker精排后，系统需要判断检索结果的可信程度，决定返回给客服的展示方式。采用**差值模式（gap）**而非绝对分数模式：

- **差值 = Top1分数 - Top2分数**：差值大说明Top1显著优于其他候选，可信度高
- **双条件判定**：差值>=gap_X AND Top1>=floor_X，防止"两个都很差但差值大"的误判

| 置信度 | 差值条件 | 底线条件 | 返回数量 | 展示建议 |
|--------|---------|---------|---------|---------|
| high | >=0.15 | Top1>=0.5 | Top-3 | 简单看看 |
| mid | >=0.08 | Top1>=0.3 | Top-5 | 需认真看 |
| low | >=0.03 | Top1>=0.15 | Top-10 | 需认真看 |
| none | 不满足以上 | - | Top-10 | 无匹配 |

**设计考量**：Reranker的绝对分数受问题长度、领域等因素影响波动大，不能作为可靠置信度。差值模式关注"Top1是否显著优于其他"，更稳定可靠。所有结果都返回给客服，置信度只影响展示优先级，不阻断服务。

### 3.6 HyDE增强检索

HyDE（Hypothetical Document Embeddings）是提升检索效果的关键技术：对知识库中的每条QA，LLM生成多种用户可能问的口语化问题，编码为向量后存入Milvus（标记is_hyde=true），检索时同时匹配原始问题和假设性问题。

**条件改写优化**：不是所有QA都需要HyDE改写。系统采用两层判断：

- **第1层规则预判（0 token）**：问题5-15字+含品牌词+含疑问词 → 判定"不需要改写"，直接跳过
- **第2层LLM判断**：规则无法判定时，调LLM输出HydeJudgeOutput（need_rewrite + reason）

这一优化能跳过约80%的标准问题，大幅节省LLM调用成本。

**HyDE两步分离**：生成（hyde_generate.py）和插入（hyde_insert.py）分离，生成依赖LLM+Embedding，插入只依赖Milvus，可独立执行和重试。

### 3.7 入库预处理流程（/api/v1/agent/process）

当新问题通过工单系统处理后，需要将处理结果标准化入库。系统通过3步Agent流水线自动完成：

**第一步：clean_text（防御性清洗）**

与检索链路相同，去除工单中的隐私信息、格式噪声等。

**第二步：structure_ingest（结构化规整+分类）**

这是入库链路的核心步骤，一次LLM调用完成多项任务：

- **问题改写**：将工单描述（如"客户张三反馈重复扣费了"）改写为标准问题格式（"重复扣费如何处理"），5-30字，提问式
- **答案结构化**：将自由文本分离为answer（面向客户话术）+ internal_process（内部操作步骤）+ feedback_dept（反馈部门）
- **分类匹配**：从知识库分类体系（MySQL动态加载）中选择category_l1/category_l2
- **分类置信度**：输出category_confidence（0.0~1.0），低于阈值触发needs_review人工审核

输出为Pydantic Schema（StructureIngestOutput），字段自动校验，保证与数据库字段对齐。

**第三步：hyde_rewrite（条件改写）**

与检索链路的HyDE相同，判断是否需要生成假设性问题。不需要改写的直接跳过。

**后处理校验**：

- 幻觉检测：改写不得引入forbidden_new_kws中的业务概念
- 关键词保留：must_preserve_kws中的词在原文出现时改写必须保留
- 校验失败时自动回退为原始文本，标记需人工审核

### 3.8 工单闭环流程

系统与CRM工单系统对接，形成完整闭环。**核心原则：所有条目入库前必须人工审核确认，定时任务不自动入库。**

1. 客服提问 → RAG未命中 → 提交工单系统（调外部CRM API）
2. 本地work_orders表存记录（status=submitted）
3. 工单系统处理（外部CRM系统，本系统不干预）
4. **定时调度器（APScheduler）**自动拉取已处理工单（调外部API），更新本地记录（status=answered）
5. Agent预处理：clean_text → structure_ingest → hyde_rewrite，更新本地记录（status=processed）
6. **去重检查**：新问题 vs 已有知识库（SequenceMatcher文本相似度，阈值0.85）
   - 疑似重复 → 标记rejected，不写入知识库
   - 非重复 → 写入qa_pairs表（**status=deprecated，待人工审核**），工单状态置deduped
7. **人工审核**（管理员在审核页面操作）：
   - 审核通过 → status=active → 双库写入（MySQL + Milvus + BM25索引重建）+ 一致性校验
   - 审核驳回 → status=archived
8. 双库一致性保障：先写MySQL拿qa_id → 向量化 → 写Milvus（重试2次）→ 仍失败则回滚MySQL(delete_qa)并抛异常；BM25重建失败仅告警不回滚

**定时调度器配置**（config/scheduler.yaml）：
- sync_and_ingest任务：每1小时执行一次，拉取+预处理+去重+写入待审核
- cleanup任务：每24小时执行一次，清理imported/rejected工单
- alert_check任务：每1分钟执行一次，检查6条告警规则
- 调度器管理API：`GET /api/scheduler/status`（状态）、`POST /api/scheduler/trigger/{job_id}`（手动触发）、`GET /api/scheduler/logs`（执行日志）

## 四、关键技术决策与实现细节

### 4.1 提示词模板化+结构化输出

**问题**：提示词写死在代码里，改一个字都要改代码重新部署；LLM返回纯文本JSON，手动解析容易出错。

**解决方案**：

1. **PromptEngine（prompt_engine.py）**：用jinja2渲染提示词，支持{{enterprise_name}}、{{brand_keywords_str}}等变量自动替换。模板优先从DB加载，60秒TTL缓存，改了DB后最多60秒自动生效。不同企业部署时只需修改DB中的模板，代码零改动。

2. **StructuredOutput（output_schemas.py）**：4个Pydantic Schema定义LLM输出格式：
   - StandardizeOutput：标准化判断（need_rewrite + reason + rewritten + rewrite_confidence）
   - StructureIngestOutput：入库结构化（question + answer + category_l1/l2 + category_confidence + internal_process + feedback_dept）
   - HydeJudgeOutput：HyDE判断（need_rewrite + reason）
   - HydeRewriteOutput：HyDE改写（questions列表）

3. **get_structured_llm()（llm.py）**：调用LangChain的with_structured_output(schema)，让LLM直接返回Pydantic对象。支持tool_call模式，不支持时自动降级为JSON解析。

### 4.2 分层漏斗架构

Agent预处理采用"规则优先+LLM兜底"的分层漏斗：

```
规则匹配（0 token，覆盖80%常见问题）
    ↓ 规则无法判定
轻量模型/正则（0 token）
    ↓ 仍无法判定
小LLM判断（少量token，输出need_rewrite）
    ↓ 需要改写
大LLM改写（完整token，输出结构化结果）
```

这种设计在保证质量的同时大幅降低LLM调用成本，尤其适合客服场景中大量标准化问题的处理。

### 4.3 模型能力注册表

不同LLM对结构化输出的支持能力不同，系统通过模型能力注册表（models.yaml llm_registry）自动适配：

```yaml
llm_registry:
  deepseek-chat:
    structured_method: function_calling
  deepseek-v4-flash:
    structured_method: none
  gpt-4o:
    structured_method: json_schema
```

优先级：agent.yaml显式指定 > 注册表 > 代码兜底(none)。切换模型时自动适配最佳结构化输出方式，业务代码无需修改。

### 4.4 领域适配设计

系统设计时充分考虑不同企业/领域的适配需求：

- **纠错表可配置**：ASR纠错表存YAML+DB，不同领域只需替换纠错条目
- **关键词列表可配置**：品牌词、业务词、疑问词等全部存DB，API热更新
- **分类体系动态加载**：从MySQL qa_pairs表自动提取分类树，新增分类无需改代码
- **提示词模板化**：PromptEngine从DB加载模板，不同领域可定制不同提示词
- **清洗规则可配置**：filler_patterns、core_patterns、clean_rules全部配置化

### 4.5 核心代码设计展示

#### 4.5.1 分层漏斗架构 — 规则清洗（clean_text.py）

```python
def _defensive_clean(text: str) -> str:
    clean_rules = get_business_config("clean_rules", [])
    for rule in clean_rules:
        text = re.sub(rule, "", text)
    text = re.sub(r"\s+", " ", text)
    text = re.sub(r"([。！？])\1+", r"\1", text)
    text = re.sub(r"[，]{2,}", "，", text)
    text = re.sub(r"(\d)[，、](\d)", r"\1.\2", text)
    return text.strip(" ，。！？、")
```

规则清洗零token处理：从DB加载正则规则，去除隐私信息/填充词/格式噪声，覆盖80%常见问题。

#### 4.5.2 三级检索架构 — RRF融合（recall.py）

```python
def rrf_merge(self, vec_results, bm25_results):
    scores = {}
    for rank, (qid, _) in enumerate(vec_results):
        scores[qid] = scores.get(qid, 0) + 1.0 / (self.rrf_k + rank + 1)
    for rank, (qid, _) in enumerate(bm25_results):
        scores[qid] = scores.get(qid, 0) + 1.0 / (self.rrf_k + rank + 1)
    return sorted(scores.items(), key=lambda x: x[1], reverse=True)

def recall(self, query_text, query_vector=None, use_hyde=True, active_qa_ids=None):
    vec_results = self.vector_recall(query_vector, use_hyde=use_hyde)
    bm25_results = self.bm25_recall(query_text)
    return self.rrf_merge(vec_results, bm25_results)
```

向量召回+BM25召回并行执行，RRF（k=60）按排名融合，不依赖绝对分数，对两路分数尺度差异天然鲁棒。

#### 4.5.3 HyDE条件改写 — 规则预判跳过（hyde_rewrite.py）

```python
def _judge_need_rewrite(question: str, answer_summary: str) -> tuple:
    # 第1层：规则预判（0 token）
    if min_len <= len(question) <= max_len:
        has_brand = any(kw in question for kw in brand_keywords + subject_keywords)
        has_qw = any(kw in question for kw in question_words)
        if has_brand and has_qw:
            return False, "问题简洁标准，跳过HyDE"
    # 第2层：LLM判断（少量token）
    result = structured_llm.invoke([HumanMessage(content=prompt)])
    return result.need_rewrite, result.reason
```

问题5-15字+含品牌词+含疑问词→直接跳过，0 token。仅边界情况调LLM，跳过约80%的标准问题。

#### 4.5.4 阈值差值判定（threshold.py）

```python
def _judge_gap(self, candidates: list[tuple]) -> tuple[str, int]:
    top1_score = candidates[0][1]
    gap = top1_score - candidates[1][1] if len(candidates) > 1 else 1.0

    if gap >= self.gap_high and top1_score >= self.floor_high:
        return "high", self.high_count
    elif gap >= self.gap_mid and top1_score >= self.floor_mid:
        return "mid", self.mid_count
    elif gap >= self.gap_low and top1_score >= self.floor_low:
        return "low", self.low_count
    else:
        return "none", self.low_count
```

差值=Top1分数-Top2分数，双条件判定（差值≥gap AND Top1≥floor），防止"两个都很差但差值大"的误判。

#### 4.5.5 AgentState状态流转（state.py）

```python
class AgentState(BaseModel):
    raw_question: str = Field(description="原始问题文本")
    question: str = Field(default="", description="处理后的问题")
    rewrite_confidence: float = Field(default=1.0)
    answer: str = Field(default="", description="处理后的答案")
    category_l1: str = Field(default="", description="一级分类")
    category_l2: str = Field(default="", description="二级分类")
    hyde_questions: list[str] = Field(default_factory=list)
    confidence: float = Field(default=1.0)
    needs_review: bool = Field(default=False)
    current_step: str = Field(default="start")

```

Pydantic BaseModel定义全状态，LangGraph节点间通过AgentState传递，字段自动校验+类型安全。

#### 4.5.6 配置中心三级降级（config_center.py）

```python
def get_business_config(key: str, default=None):
    # 1. 内存缓存（TTL 60秒）
    if key in _cache and (now - _cache_ts.get(key, 0)) < _ttl:
        return _cache[key]
    # 2. DB配置中心（优先）
    db_value = mysql.get_config(key)
    if db_value is not None:
        _cache[key] = db_value
        return db_value
    # 3. YAML本地兜底
    yaml_value = get_config().get("prompts", {}).get(key)
    return yaml_value if yaml_value is not None else default
```

DB→缓存→YAML三级降级：DB修改后60秒自动生效，DB不可用时降级到YAML，保证服务不中断。

## 九、创新点总结

1. **阿里云NLS API+热词表的语音智能提炼**：阿里云NLS实时语音识别+热词表适配客服行业黑话和专业术语，搭配可配置纠错表，实现语音→标准化问题的端到端智能提炼

2. **双路召回+RRF+Reranker三级检索架构**：语义召回与关键词召回互补，Reranker精排消除融合偏差，Recall@1从58%提升至89%

3. **条件HyDE改写**：两层判断（规则预判+LLM兜底）跳过80%不需要改写的标准问题，节省LLM调用成本

4. **差值阈值判定**：用Top1-Top2差值替代绝对分数作为置信度，避免分数波动导致的误判

5. **提示词模板化+结构化输出**：提示词存DB可热更新，LLM输出Pydantic Schema自动校验，改提示词不改代码

6. **分层漏斗架构**：规则优先+LLM兜底，80%问题零token处理，兼顾效率和质量

7. **完整提示词迭代流水线**：版本管理+黄金数据集评估，提示词改动可追溯可回退

8. **企业级配置分层+领域适配**：DB业务规则→YAML基础设施→.env敏感信息，热更新无需重启；纠错表/关键词/分类/提示词全部可配置，不同企业部署代码零改动

9. **工单闭环+知识自迭代**：未命中→工单→Agent预处理→人工审核→入库，知识库持续扩充，重复工单量持续降低

10. **异常告警机制**：内存滑动窗口指标采集+6条告警规则+去重抑制+站内告警/webhook通知，关键链路异常早发现早处理，保障系统运行可观测
