# 高并发演进路线

## 当前架构（挑战杯演示级，QPS < 50）

```
客户端 → uvicorn(1 worker) → FastAPI → MySQL(连接复用) → Milvus Lite(单文件)
                                              ↓
                                    Embedding/Reranker(进程内加载)
```

已具备的并发基础：
- MySQL线程级连接复用（threading.local，每线程1连接，自动重连）
- active_qa_ids TTL缓存（30秒刷新，避免每次查MySQL）
- Reranker每次从MySQL实时查（不依赖启动时快照，数据实时一致）
- BM25/Milvus检索支持active_qa_ids过滤（软删除实时生效）

## 第一阶段：单机优化（QPS 50-200）

改动点：
1. **uvicorn多worker**：config.yaml `server.workers: 4`，利用多核
2. **Milvus Standalone**：替换Milvus Lite，支持多进程并发读+并发写
3. **Gunicorn + Uvicorn**：生产级进程管理，pre-fork模型
4. **MySQL连接池**：换用 SQLAlchemy Engine（真正的连接池，max_overflow控制）

```bash
# 启动命令
gunicorn main:app -w 4 -k uvicorn.workers.UvicornWorker -b 0.0.0.0:8000
```

```
客户端 → Gunicorn(4 worker) → FastAPI → MySQL(连接池) → Milvus Standalone(gRPC)
```

## 第二阶段：缓存加速（QPS 200-500）

改动点：
1. **Redis缓存层**：
   - 热门query结果缓存（TTL 5分钟，key=standardized_query）
   - active_qa_ids缓存（替代内存TTL，多worker共享）
   - BM25索引快照（避免每次启动重建）
2. **Embedding服务分离**：独立部署，多进程共享模型显存
3. **Reranker批量化**：积累N个请求后批量predict，提高GPU利用率

```
客户端 → Gunicorn → FastAPI → Redis(缓存) → MySQL → Milvus Standalone
                                ↓ miss
                          Embedding Service(独立进程)
                                ↓
                          Reranker Service(独立进程)
```

## 第三阶段：分布式部署（QPS 500+）

改动点：
1. **K8s + Helm**：容器化部署，HPA自动扩缩容
2. **Milvus分布式**：Coordinator + DataNode + QueryNode + IndexNode
3. **Redis Cluster**：分片缓存
4. **MySQL读写分离**：主写从读
5. **模型服务**：Triton Inference Server / vLLM，GPU共享+动态批处理
6. **异步化**：FastAPI异步路由 + asyncio，检索/重排并行化

```
                    ┌─ Pod1(FastAPI) ─┐
                    ├─ Pod2(FastAPI) ─�-→ Redis Cluster → MySQL主从
客户端 → Ingress ──┤                 ─→ Milvus分布式集群
                    ├─ Pod3(FastAPI) ─┐
                    └─ Pod4(FastAPI) ─┘
                                        ↓
                              Triton/vLLM(GPU服务)
```

## 关键设计决策（已为演进预留）

1. **连接池用threading.local**而非全局池：多worker时每个进程独立池，无锁竞争
2. **Reranker每次查MySQL**而非启动快照：多worker时数据一致，无需同步缓存
3. **active_qa_ids有TTL缓存+主动失效**：软删除后立即生效，TTL兜底防漏刷
4. **config.yaml支持环境变量**：K8s ConfigMap/Secret直接注入，不改配置文件
5. **BM25索引进程内构建**：多worker各自一份，内存换简单性；演进到Redis后统一
